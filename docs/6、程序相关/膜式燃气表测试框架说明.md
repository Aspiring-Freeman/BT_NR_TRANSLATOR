# 膜式燃气表测试框架说明 (NB_18_DiaphragmGas_Test)

> 适用版本: v4.1.6+
> 路径: `Src/Test/NB_18_DiaphragmGas_Test/`

---

## 1. 设计目标与总体思想

膜式燃气表测试模块要把"**一连串带超时、带重试、带跳过、带电源监控的硬件测试步骤**"按可配置的顺序跑完。早期实现是几千行的 `if-else / switch` 状态机,很难加新测试项,所以重构为**回调表驱动 (Table-Driven State Machine)**:

- **流程定义** = 一张数组 `diaphragm_step_table[]`,每行描述一个步骤(名称、handler、超时、重试、跳过条件、失败策略)。
- **主循环 `diaphragm_test_loop()`** 只负责通用调度:超时、重试、电源监控、步骤跳转。
- **每个步骤的业务逻辑** 写在自己的 handler 函数里,handler 通过返回(`step_success` / `step_fail` / `goto_step`)告诉框架下一步去哪。
- **协议事件** 通过 `device_protocol` 的回调机制异步设置位标志 (`events_received`),handler 在轮询时检查标志。

这样**新增测试项 = 写一个 handler + 在表里加一行**,主循环零修改。

## 3. 核心数据结构

### 3.1 步骤描述符 `DiaphragmStepDescriptor_t`

每张表项都是这个结构体:

```c
typedef struct {
  const char *name;                  // 步骤名 (日志显示)
  const char *description;           // 详细描述
  DiaphragmStepHandler handler;      // 轮询 handler (主循环每 tick 调一次)

  uint16_t timeout_ms;               // 单步超时;0=不限
  uint8_t  max_retry;                // 最大重试次数;0=不重试

  DiaphragmTestStep_t next_step;     // 成功后跳转;DIAPHRAGM_NEXT_AUTO=下一步
  DiaphragmExecuteFunction on_enter; // 进入时执行一次 (发协议/触 IO)
  DiaphragmExecuteFunction on_retry; // 重试时执行;NULL 复用 on_enter

  DgmTestMode_t test_mode;           // IDLE / NORMAL / LOW_POWER 决定功耗监控

  uint8_t *skip_status_ptr;          // 跳过判定指针;NULL=不跳过
  uint8_t  skip_when_equals;         // *skip_status_ptr == 此值 -> 跳过

  FailAction_t fail_action;          // STOP / CONTINUE / GOTO / RETRY_THEN_CONTINUE
  DiaphragmTestStep_t fail_goto_step;// FAIL_ACTION_GOTO 的目标
} DiaphragmStepDescriptor_t;
```

### 3.2 运行时状态 `DiaphragmTestRuntime_t`

集中所有运行变量,**避免散落的全局变量**:

- 硬件初始化状态 (`hardware_init_pending` / `hardware_init_failed` / `init_retry_count`)
- 步骤执行状态 (`step_entered` / `step_executing` / `sub_step` / `retry_count`)
- 协议事件位掩码 `events_received` (`DGM_EVT_SELF_CHECK | DGM_EVT_BOARD_INFO | …`)
- 协议数据缓存 (`board_info`, `io_status`)
- 运行功耗监控 (`last_power_check_tick`, `running_power_ua`, `power_check_fail_count`)
- 时间管理 `DgmTimeManager_t` (软件延时 + 总超时 + 单步超时 + 成功延时关电)
- 测试结果 (`fail_reason`, `fail_step`, `test_completed`, `waiting_power_off`)

### 3.3 测试结果 `DiaphragmTestResult_t`

`#pragma pack(1)`,**与上位机协议字节对齐**,直接序列化发给 PC。

### 3.4 IO 状态 `DiaphragmIOStatus_t`

记录开盖检测、119 报警、计量霍尔在测试**前后**的电平,用于"测试前/后状态对比"判定。

### 3.5 组件状态 `diaphragm_component_status`

可选模块的"是否需要测试"配置,值定义:

| 值 | 含义 |
|---|---|
| `0` (`DIAPHRAGM_COMPONENT_STATUS_FAIL`) | 已测试,失败 |
| `1` (`DIAPHRAGM_COMPONENT_STATUS_PASS`) | 需要测试 / 测试通过 |
| `2` (`DIAPHRAGM_COMPONENT_STATUS_UNTESTED`) | 跳过(不测试) |

会被 1001 协议响应里的"附件信息"动态更新。

## 4. 测试步骤总览 (`DiaphragmTestStep_t`)

```text
WAIT (待机,慢闪 LED)
 ↓ 收到测试触发
START                           ─ 输入电压 / 各路电压基线检测
 ↓
MODULE_GPRS_VOLTAGE_TEST        ─ GPRS 3.6V 启动等待
 ↓
MODULE_SUCCESS_RESPONSE_WAIT    ─ 等模块 1000 协议响应
 ↓
IO_STATUS_CHECK                 ─ 1001 板级信息 + IO 初始电平 + 附件清单
 ↓
┌──── 可选组件 (skip_status_ptr 命中则跳过) ────┐
│ BLUETOOTH_TEST                                  │
│ COVER_CHECK                                     │
│ IC_MODULE_TEST                                  │
│ METERING_MODULE_TEST                            │
│ 119_WARNING_TEST                                │
│ TEMP_PRESSURE_SENSOR_TEST                       │
│ SECOND_VALVE_TEST                               │
│ TILT_SWITCH_TEST                                │
└────────────────────────────────────────────────┘
 ↓
DEFAULT_VALVE_TEST              ─ 阀门电压(必测)
VALVE_POSITION_TEST             ─ 阀门到位
TEMP_CHECK                      ─ 温度压强读数
NB_CONNECT                      ─ NB-IoT 连接
IMEI_READ                       ─ IMEI / IMSI / ICCID
CLOSE_IR                        ─ 关红外(为下一步功耗准备)
UART_CONNECT_TEST               ─ UART 通信回环
POWER_CHECK                     ─ 静态功耗 (LOW_POWER 模式;故意放最后)
 ↓
END                             ─ 关电 / 汇总结果 / 等 PC 查询
 ↓
WAIT
```

> **注意顺序**:`POWER_CHECK` 必须在 `CLOSE_IR` 之后,否则红外发射会污染功耗读数。

## 5. 主循环执行模型 (`diaphragm_test_loop`)

每次主循环 tick 按这个**优先级**执行:

```text
1.  waiting_power_off?         成功/失败后保持供电期 → 仅监控 5V,到时关电
2.  RetryManager 延时中?       等延时;若期间收到响应则提前取消
3.  TimeManager 软件延时中?    未到 → return
4.  全局测试超时?              → step_fail(DGM_TOTOAL_TIMEOUT)
5.  硬件初始化未完成?          → diaphragm_hardware_init() (内部带 5 次重试)
6.  取当前步骤描述符 step_desc
7.  IDLE 模式?                 (WAIT / END) 跳过监控,END 仍要执行 handler
8.  NORMAL 模式?               每 500ms 检查运行功耗 + 第二节点 5V
                               (任一异常立即 step_fail)
9.  LOW_POWER 模式?            跳过功耗监控 (步骤自己测功耗)
10. 单步超时 + step_entered?   交给 RetryManager 决定:
                                 RETRY_OK       → 触发重试 (回调里执行 on_retry)
                                 RETRY_EXHAUSTED→ step_fail(DGM_FAIL_TIMEOUT)
                                 NO_RETRY_CONFIG→ step_fail(DGM_FAIL_TIMEOUT)
11. skip_status_ptr 命中?       step_skip("附件不支持")
12. step_desc->handler();      跑业务
```

**每次 `diaphragm_goto_step()` 都会重置 step 级状态**(`step_entered`、`step_executing`、`sub_step`、`retry_count`、`events_received`、`TM_StartStepTimeout()`),保证 handler 重入安全。

## 6. 步骤定义宏 (写新步骤时用这些,**不要直接填结构体**)

| 宏 | 含义 | 失败策略 |
|---|---|---|
| `STEP_REQUIRED(name, desc, handler, timeout)` | 必测 | STOP |
| `STEP_REQUIRED_RETRY(name, desc, handler, timeout, retry)` | 必测带重试 | STOP |
| `STEP_REQUIRED_SOFT(...)` | 必测但失败继续 | CONTINUE |
| `STEP_REQUIRED_RETRY_SOFT(...)` | 必测带重试,失败继续 | CONTINUE |
| `STEP_REQUIRED_RETRY_ENTER(...)` | 必测带重试 + on_enter (常用于"进入时发协议") | STOP |
| `STEP_REQUIRED_RETRY_ENTER_CONTINUE(...)` | 同上,失败继续 | CONTINUE |
| `STEP_OPTIONAL(name, desc, handler, timeout, comp_ptr)` | 可选,`*comp_ptr == UNTESTED(2)` 时跳过 | CONTINUE |
| `STEP_SYSTEM(name, desc, handler, timeout, next, mode)` | 系统步骤 (WAIT/END,test_mode 显式给) | — |
| `STEP_LOW_POWER(name, desc, handler, timeout, retry)` | 低功耗模式步骤 | STOP |
| `STEP_CUSTOM(...)` | 完全自定义,所有字段都填 | 任意 |

`COMP_BLUETOOTH` / `COMP_COVER` / `COMP_IC_MODULE` / ... 是 `&diaphragm_component_status.xxx` 的快捷宏,直接传给 `STEP_OPTIONAL`。

## 7. handler 编写约定 (重要)

```c
void diaphragm_handle_xxx(void) {
  // ── A. 一次性初始化 (只在首次进入时执行) ──
  if (!diaphragm_runtime.step_executing) {
    common_print_step_header("XXX 测试");          // 打印分隔头
    DGM_SendXxxRequest();                          // 例:发协议请求
    diaphragm_runtime.step_executing = 1;
    diaphragm_runtime.step_entered   = 1;          // ← 必须置位,主循环才会查超时
    return;
  }

  // ── B. 等待协议事件 / IO 变化 (轮询) ──
  if (diaphragm_runtime.events_received & DGM_EVT_XXX) {
    // 处理响应
    if ( /* 通过 */ ) {
      common_print_step_footer("通过");
      diaphragm_step_success();                    // → 自动跳 next_step
    } else {
      common_print_step_footer("失败:xxx");
      diaphragm_step_fail(DGM_FAIL_XXX);           // → 按 fail_action 跳转
    }
    return;
  }

  // ── C. 子状态机分支 (sub_step) ──
  switch (diaphragm_runtime.sub_step) {
    case 0:
      // 阶段 0...
      diaphragm_runtime.sub_step = 1;
      diaphragm_set_delay(300);                    // 等硬件稳定
      break;
    case 1:
      // 阶段 1...
      break;
  }
}
```

**核心规则**:
1. handler **不阻塞**,`while(condition)` 严禁出现。要等就 `return`,主循环下一 tick 再来。
2. **必须置 `step_entered = 1`**,否则单步超时检测不会触发(防止刚进步骤就被超时)。
3. 用 `step_executing` 防重入(防止 on_enter 被多次调用发了多帧请求)。
4. 退出步骤只能用 `diaphragm_step_success()` / `diaphragm_step_fail()` / `diaphragm_step_skip()` / `diaphragm_goto_step()`,**不要直接改 `diaphragm_test_step`**。
5. 长 IO 等待用 `diaphragm_set_delay(ms)`,不要 `for` 空循环。

## 8. 三种测试模式 `DgmTestMode_t`

| 模式 | 何时用 | 主循环行为 |
|---|---|---|
| `DGM_MODE_IDLE` | WAIT / END | 不监控功耗;END 仍执行 handler 关电 |
| `DGM_MODE_NORMAL` | 大部分步骤 | 每 500ms 检查运行功耗(阈值 50mA) + 第二节点 5V |
| `DGM_MODE_LOW_POWER` | `POWER_CHECK` | 跳过通用功耗检查,**步骤自己**做 ADC 读数判定静态电流 |

NORMAL 模式下,运行功耗连续 ≥ `RUNNING_POWER_FAIL_THRESHOLD` (3) 次异常 → 直接 `step_fail(DGM_FAIL_RUNNING_POWER)`。

## 9. 重试机制 (`retry_manager.c` + `RetryManager` 全局实例)

```text
单步超时 (TM_IsStepTimeout && step_entered)
  ↓
RM_TryRetry(RM_REASON_TIMEOUT)
  ↓
判断 step_desc->max_retry
  ├─ 还有次数 → RM_RESULT_RETRY_OK
  │    ↓
  │    回调 on_diaphragm_retry_reset() (清 events_received / step_executing / sub_step)
  │    可选延时 (RM 内部配置)
  │    回调 on_diaphragm_retry_action() → 调 step_desc->on_retry (或 on_enter)
  │
  ├─ 用尽          → RM_RESULT_RETRY_EXHAUSTED → step_fail(DGM_FAIL_TIMEOUT)
  └─ 没配 max_retry → RM_RESULT_NO_RETRY_CONFIG → step_fail(DGM_FAIL_TIMEOUT)
```

`on_diaphragm_retry_reset` / `on_diaphragm_retry_action` 在 [diaphragm_test_helpers.c](../../Src/Test/NB_18_DiaphragmGas_Test/diaphragm_test_helpers.c)。

## 10. 协议事件流 (`device_protocol` ↔ test 模块解耦)

```text
UART RX ISR
   ↓ 字节入环形缓冲
device_protocol 解析任务
   ↓ 完整帧 + 校验通过
DGM_EventCallback (在 protocol 层调度)
   ↓
diaphragm_on_protocol_event(event)            ← diaphragm_test_protocol_events.c
   ↓ switch (event->type)
   设置 diaphragm_runtime.events_received |= DGM_EVT_XXX
   缓存协议数据到 diaphragm_runtime.board_info / io_status / ...
   ↓
主循环下一 tick → handler 检查位掩码 → 业务处理
```

**协议事件回调只做"接收 + 设标志 + 缓存数据"**,不做任何业务判定 — 业务全在 handler 里。注册入口:`diaphragm_register_protocol_callback()`。

## 13. 失败处理策略 `FailAction_t`

`step_desc->fail_action` 决定 `diaphragm_step_fail()` 后的跳转:

| 值 | 行为 |
|---|---|
| `FAIL_ACTION_STOP` (默认) | 立即跳到 `DIAPHRAGM_END`,记录 `fail_reason` |
| `FAIL_ACTION_CONTINUE` | 记录失败但继续下一步(用于"软失败",如可选模块) |
| `FAIL_ACTION_GOTO` | 跳到 `fail_goto_step` 指定的步骤 |
| `FAIL_ACTION_RETRY_THEN_CONTINUE` | 重试用尽后继续(而不是停) |
